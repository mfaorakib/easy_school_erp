# EasySchool ERP — Build Log

Running record of what has been built. Feature scope & completeness are tracked in
[COVERAGE-MAP.md](COVERAGE-MAP.md); business logic in [business-logic/](business-logic/).

Rule: rebuild of the reference system, **single-school**, **same business logic**, cleaner code,
new design. **Only SaaS subscription/billing excluded** — every other module (incl.
Inventory) is in scope. **Multi-language** is in scope.

## Done

### Phase 0 — Foundation ✅
- Laravel 12 + `nwidart/laravel-modules` + `spatie/laravel-permission`, MySQL `easyschool_erp`.
- Core infra `app/Core/`: `Context` (active academic year), `AcademicYearScope`, `BelongsToAcademicYear` trait.

### Phase 7 — Inventory ✅
- Module **Inventory** (7 tables, global): item_categories, suppliers, item_stores, items, item_receives (stock-in), item_issues (stock-out to user, returnable), item_sells (stock-out by sale).
- **Stock is DERIVED** from the ledger (Σ received − Σ issued-not-returned − Σ sold) via `Item->stock` accessor — cleaner than the reference's mutable `total_in_stock` column (no drift; identical outcomes). `InventoryService`: receive, issue (guarded: can't exceed stock), returnIssue, sell (guarded too — reference had no sell guard; we add it per the analysis's recommendation).
- UI: Items/Categories/Suppliers/Stores CRUD + Receive / Issue / Sell consoles. Nav "Inventory".
- Built with **3 parallel agents** (lookups CRUD · items CRUD · movements) → controllers+views; main loop owned routes/nav/lang/seeder/verify. Spec `docs/business-logic/10-inventory.md`. Verified: receive 100→issue 30→sell 20→stock 50; over-issue blocked.

### Phase 45 — Migration consolidation (dev-phase cleanup, no schema change) ✅
- User asked to fold every later "add column to X table" migration back into its original `create_X_table` migration, since the project is still in active local development (never deployed, no real users) — a common, sensible cleanup at this stage so the migration history doesn't accumulate dozens of small bolt-on files for every table across the whole project's build history.
- **The one real hazard, understood before touching anything**: Laravel runs migrations in filename order. Folding a later column's FOREIGN KEY into an EARLIER `create_X_table` migration is only safe if the referenced table's own create-migration is dated even earlier still (or it's a self-reference, which MySQL/InnoDB supports fine within one `CREATE TABLE`) — otherwise `migrate:fresh` would try to create a FK against a table that doesn't exist yet. Every agent was given this exact rule and told to check it case-by-case rather than fold blindly.
- Captured a full **structural schema baseline before touching anything** — not a raw `SHOW CREATE TABLE` text dump (which would flag harmless column-order differences as false positives), but `information_schema`-sourced column/index/foreign-key lists per table, so the final verification could be genuinely order-insensitive.
- Consolidated across the whole app (~184 migration files → 137): every module's `create_*_table` migrations now carry their full final column set — every `softDeletes()` added system-wide in Phase 44, every historical bolt-on column (`unique_id` on students, bank details + `leaving_date` on staff, `receipt_no`/`refunded_amount` on fee_payments, the whole Accounting adjustment-support column set including the self-referencing `parent_transaction_id`, voucher/return columns on Inventory, and many more) folded directly into the table that owns it.
- **Exactly one genuine FK-ordering hazard found and correctly left alone, not force-folded**: `student_documents.document_type_id` (added `2025_07_23`) references `document_types`, which isn't created until a migration also dated `2025_07_23` but later in sequence — while `student_documents` itself was created on `2025_07_21`, well before `document_types` exists. Folding this FK into the earlier `create_student_documents_table` would break `migrate:fresh` outright. Left as its own standalone add-migration, exactly as it should be — a good outcome, not a shortfall, since forcing a fold here would have been the actual mistake.
- Also cleanly handled two migrations that weren't simple "add a column" cases: Accounting's `restrictOnDelete()` conversion (from the earlier delete-safety bug fix) got folded directly into `account_transactions`/`account_transfers`' original FK definitions (so they're `restrictOnDelete()` from the start, no separate alter-migration needed), and `payment_methods`' add-migration had `->after()` positional modifiers that are meaningless/invalid inside a fresh `Schema::create()` (column order there is just declaration order) — correctly dropped rather than carried over literally.
- Built with 5 parallel agents, split by module cluster, each given the exact same FK-ordering safety rule and told explicitly not to run any migration command themselves (to avoid a concurrent-migration race on the shared dev database) — the main loop ran one single `migrate:fresh --seed` only after every agent had finished.
- **Verified with a genuinely rigorous method, not spot-checks**: after consolidation, ran `migrate:fresh --seed` clean (zero errors across all 137 files + every seeder), then re-captured the same `information_schema` structural snapshot and diffed it programmatically against the pre-consolidation baseline — order-insensitive, covering every column (name/type/nullable/default/extra), every index (columns + unique-ness), and every foreign key (column → referenced table/column) across all 146 tables. **Result: 0 tables missing, 0 tables added, 0 structural differences anywhere** — the schema is byte-for-byte equivalent to before, just reorganized into far fewer files. Followed up with a real-HTTP smoke test across 10 pages spanning every major module (Dashboard, Students, Staff, Inventory receive/sell, Fees collect, Accounting transactions, Payroll payslips, Sidebar Manager, Student Profile) — all 200, zero new log errors. - User asked whether the system had a preview for documents beyond ID cards/certificates (e.g. clearance letters, appreciation letters) — answer was: any new document type can already be created with zero code (the `CertificateTemplate` system is fully generic), but there was no preview and no real visual design control — every certificate looked identical (same hardcoded gold double-border, same serif font) regardless of template, and the only way to "see" a template was to actually generate it for a real person, permanently consuming a real document number if one was configured. - **Design controls, not just content**: `certificate_templates` gained `accent_color` (hex, drives the border/heading/divider color), `font_family` (serif/elegant/sans — three real, self-hosted system-font stacks, no Google Fonts/CDN dependency added), and `border_style` (classic double-frame/simple single-line/none). `Modules/Documents/resources/views/print/certificate.blade.php` — the ONE shared rendering template every certificate (Transfer/Experience/Character/Appointment Letter, and any future one) already goes through — now computes its CSS from these three fields instead of hardcoded values, so every template can look genuinely different without touching any Blade file.
- **Preview that can never consume a real document number**: `DocumentService::previewBody()` fills the SAME `{{placeholder}}` body a real certificate uses, but with fixed sample data ("John Doe", a fake `TC-SAMPLE-00001`-style document number) — it never calls `documentNumber()`/touches `DocumentIssuance` at all, so clicking Preview a hundred times never burns a real serial number. `CertificateTemplateController::preview()` builds an UNSAVED, in-memory `CertificateTemplate` straight from the current form submission (not from the database) — including a just-picked-but-not-yet-saved image file, rendered as a `data:` URI (no temp file ever written to disk; `DocumentService::media()` gained a one-line pass-through for `data:` values) — so Preview always shows exactly what Save would produce, even for changes not yet saved. Wired to the form via a second `<button formaction="…preview" formtarget="_blank" formnovalidate>` on the SAME `<form>` (not a separate form/JS) — the same one-form-two-destinations trick as everywhere else in this app that needs "do X" vs "do X and show me," opening in a new tab exactly like every other print/receipt action already does.
- No agents this phase — the whole feature is five tightly-coupled files in one module (migration, model, service, controller, two views) with a genuinely fiddly correctness requirement (preview must reflect unsaved state, including files, without ever touching real numbering) that benefited from one continuous train of thought rather than a handoff.
- **Verified end-to-end via real HTTP with before/after counts, not just "it rendered"**: submitted a Preview request with an unsaved heading, custom body, a distinct accent color, and border_style=none — confirmed the response showed the UNSAVED heading, the sample name, a `TC-SAMPLE-00001`-style number, the new color, and `display:none` on the frame — then confirmed `DocumentIssuance::count()` was identically `0` before and after. Separately, actually SAVED a template with a different accent color + simple border and generated a REAL certificate for a real student — confirmed the live output picked up the saved color and border style correctly, proving the design system works identically for both the safe preview and the real generation path (same shared template, same shared Blade view, no drift possible between what you preview and what you get).

- **Follow-up fix**: user reported the side-panel preview showing blank in the real browser. My own curl-based verification had genuinely passed (200, correct rendered content) — the gap was that curl never reproduces what a real `<form>` submission sends. Root-caused with a real headless-browser test (Playwright driving actual Chromium, not curl): the edit form's Preview button lives inside the same `<form>` as the real Update action, and an edit form for an existing template carries a hidden `@method('PUT')` spoofing field for that Update action — every submission from that form, including via the Preview button's `formaction`, carries `_method=PUT` along with it, so Laravel re-interprets the "POST the Preview button meant to send" as a PUT before routing. The PUT request then fell through to the resource's `PUT certificate-templates/{certificateTemplate}` route (registered before the preview route), which greedily matched the literal segment "preview" as the `{certificateTemplate}` id, failed to find such a template, and Laravel auto-404'd on the failed model binding — the exact same literal-vs-`{param}` route-ordering class of bug already documented from the Staff Portal phase. Fixed by (1) registering the preview route to accept both POST and PUT, and (2) moving it to before the `Route::resource(...)` call so the literal segment is tried first. **Lesson reaffirmed**: a curl test that manually constructs its own POST body can silently miss form-mechanics bugs (hidden spoofing fields, multi-button-one-form quirks) that only surface from an actual `<form>` submission — when a user reports something a curl-verified feature "doesn't do," reproduce it with a real browser (Playwright) before assuming the report is wrong.
